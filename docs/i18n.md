# Languages

Solid Memo speaks English (`en`), Swedish (`sv`) and Korean (`ko`).
Every text the app
itself shows comes from a message file; text that comes with the data —
deck titles and descriptions, card text — is shown as the data has it,
in the language the user says it is in (see
[Text in the user's languages](#text-in-the-users-languages)).

## Which language

`pickLocale` ([locale.ts](../packages/domain/src/locale.ts)) decides, in
order:

1. the language the user chose — with the flags at the top of every
   screen, or under Language in the study preferences — kept on
   this device by the `LanguagePreference` port
   ([localStorageLanguagePreference.ts](../packages/browser/src/localStorageLanguagePreference.ts),
   key `solid-memo:language`) — not in the pod, since the sign-in
   screens need it before any pod is reached;
2. else the first of the browser's preferred languages
   (`navigator.languages`) the app speaks — `sv-SE` counts as `sv`;
3. else English.

`AppShell`, the shell of Solid Memo and of the [Studio](studio.md), sets `<html lang>` to it. Deck and card text is shown in the
same language, else the browser's, else English, else the first
language it has (`shown` in
[langText.ts](../packages/domain/src/langText.ts)); text in another
language than the page's is marked with its own `lang` (`readerLang`,
`ReaderText`), none for untagged text or text in no language (`zxx`).

A deck's keywords, several per language, are shown only in the chosen
language: every keyword under a tag with its primary subtag (`sv`,
`sv-se`, `sv-fi` for Swedish), with those in no stated language
(untagged and `zxx`), each once (`keywordsIn` in
[keywords.ts](../packages/domain/src/keywords.ts)). There is no
fallback: a deck with none of those shows no keywords. Library decks
carry keywords in English and Swedish, and in Korean only where a deck
adds them, so a Korean reader sees keywords only on a deck that has
Korean ones, and on most decks none.
The library's search still looks through the keywords of every
language, as it does titles and descriptions.

## Text in the user's languages

Text the user writes — a deck's name, description and keywords, a
card's sides, notes, label and picture descriptions — is saved
language-tagged, one value per language (keywords: a comma-separated
list per language), in whatever language the user says it is in (deck
format 6, card format 5: [shapes.md](shapes.md)). The page's language
says nothing about it: an English speaker on a Swedish page types
English. So:

- **Every field has a language picker** (`LangTextField` with
  `LanguagePicker` in [packages/ui/src/ui](../packages/ui/src/ui)): a button
  saying the language ("Language: Swedish", or "not stated") that opens
  in place onto radios — the text's own language, what the deck uses,
  the languages chosen recently on this device, the page's language,
  English, Swedish, the browser's languages, "No language (codes,
  numbers, symbols)" (`zxx`) and any other by its code, checked by
  `canonicalTag` ([languageTag.ts](../packages/domain/src/languageTag.ts)).
  A translation is a row of its own, with its own picker; changing the
  language moves the text without retyping it.
- **Nothing is chosen from the page.** A language is preselected only
  from evidence: the text's own tag; on a card, the language the last
  card added in the same form had (sticky), else the one the deck's
  cards use most for that part (`usualTag`, through `deckLanguages` in
  [deckLanguages.ts](../packages/domain/src/deckLanguages.ts)); for a
  note, label or picture description, else the one chosen last on this
  device; for a deck's name, the one chosen last on this device. The
  recent choices are kept in the browser, not the pod
  ([remembered.ts](../packages/ui/src/ui/remembered.ts), keys
  `solid-memo:recentLanguages.deck` and `solid-memo:recentLanguages.own`).
  Choosing a language for an empty field fills the untouched empty
  fields of the same kind in the form.
- **Text the user writes or changes always has its language.** Saving
  text whose language is not chosen is refused (`textNeedsLanguage`),
  and focus goes to that field's picker. The app never writes untagged
  text anew, nor copies text under English on its own.
- **Tags are stored in lower case** (`pt-br`), as the pod reads them;
  they are named through `Intl.DisplayNames` (`languageLabel`: "Swedish
  — svenska (sv)"), a tag Intl cannot name shown as itself.
- **Text over several lines keeps its breaks.** A card's text saved
  with a line break (a line feed or a carriage return), in any language,
  is edited in a textarea, and stays one in that editor even once a save
  drops the breaks, so focus stays where it is. That holds for every
  card text, the label and the picture descriptions too, though they
  are meant as single lines: editing never drops a break. A card in
  Markdown has its sides and notes in textareas whatever they hold
  ([markdown.md](markdown.md#writing-markdown-in-the-app)). A deck's
  description is always a textarea. In a textarea Enter starts a new
  line and Ctrl+Enter or ⌘+Enter submits the form, as the textarea
  states (`aria-keyshortcuts`).
- **An input method's keys are its own.** While one composes text
  (Korean, Japanese or Chinese, say), the Enter or Escape that commits
  or cancels it does nothing in the app (`composing`: the event's
  `isComposing`, or keyCode 229, which is all Safari gives once the
  composition has ended). That holds for every Enter or Escape handled
  while a field may have the focus: Ctrl+Enter in a textarea, Enter and
  Escape in a language picker, Escape in a name edited in place, Escape
  on an enlarged picture. A form's own submit on Enter is left to the
  browser, which commits the syllable first.

Older data may not say its language: card sides saved untagged, as the
app wrote them before card format 5, and keywords saved before deck
format 6. Their language is not guessed. Untagged keywords are kept, or
removed, as they are; a keyword added or changed needs its language.
The deck's page says so while any is left (`DeckLanguagesNotice`),
linking to the Languages section of the deck's preferences
(`DeckLanguagesSection`), where the untagged fronts or backs are given
one language at once (`stateCardLanguages`); the Browser marks the
cards with a side in no stated language and can list only those
(`languages=unstated` in its URL). Text still as its library release
has it is left alone, so a later release can update it.

The same words under several languages are text in each of them, and
are accepted as they are: "Stockholm"@en with "Stockholm"@sv, like
"1969"@sv with "1969"@it. That includes the identical English copies
the app wrote while the formats required English: the app cannot tell
them from a real translation, so they are left in the data untouched,
neither flagged nor offered for removal. Each language is an entry of
its own in the editor, edited, retagged or removed like any other
translation.

The deck's page weighs its text itself (`deckLanguageIssues` over
`deckLanguages`, pure domain functions) from the
cards it has read already and the deck's library release
(`UseCases.deckRelease`), rather than through a use case of its own
that would read the cards a second time. When the release cannot be
read, the page cannot tell the library's text from the user's: if the
deck's text holds none to settle even counting the library's, nothing
is said; otherwise the notice says the check could not be made, rather
than counts, and still links to the Languages section, which shows why.

## Formatted text

Text in Markdown ([markdown.md](markdown.md)) changes nothing of the
above: each language's value is its own Markdown document, under its own
tag, and every rule here holds of it as of plain text — `shownTag`,
`textNeedsLanguage`, one text per language, a distractor in the back's
languages. A code block inside `@en` text keeps `@en`, and a code-only
back may be `zxx`. The card editor hints at each language's text under
that text, and its preview shows the main one, the one being written.

The app's own words about Markdown are messages like any other:
`cardContentFields.markdown*` and `.preview*` for the editor,
`markdownHelp.*` for its cheat sheet (the syntax itself is code, the
same in every language), `markdownProblem.*` for each problem
`markdownProblems` names, and `markdown.*` for the names of a code block
and a table region and a link's host.

## Messages

[packages/ui/src/i18n/en.json](../packages/ui/src/i18n/en.json),
[sv.json](../packages/ui/src/i18n/sv.json) and
[ko.json](../packages/ui/src/i18n/ko.json) hold one namespace per
component (`deckList`, `instancePicker`, …), a few shared ones
(`common`, `language`, `footer`), and `studio` for the
[Studio](studio.md)'s own screens, in `apps/studio`, and the page's
while it loads them. Components read them through
`useI18n()` ([i18n.tsx](../packages/ui/src/ui/i18n.tsx)):

```tsx
const { t, tx, readerText, formatDate, directionLabel } = useI18n();
t("deckList.heading");                          // "Decks"
t("common.cardCount", { count: 3 });            // "3 cards" — a plural message
tx("app.loggedInAs", { name: <ExternalLink … /> }); // markup inside a sentence
```

- A message's `{name}` placeholders are filled from the values given.
- A plural message gives a form for each plural category of its
  language — `{ "one": …, "other": … }` in English and Swedish, only
  `{ "other": … }` in Korean — picked by `count` through the language's
  plural rules (`Intl.PluralRules`). A message without a count takes
  *other*.
- A sentence with a link in it stays one message (`tx`), so a language
  can put the link where its word order needs it.
- Keys are string literals, typed from `en.json`: a misspelt key fails
  the type check.

Tests in [i18n.test.tsx](../packages/ui/src/ui/i18n.test.tsx) hold
every other message file to exactly the keys and placeholders of
`en.json`, and every key the source asks for to one `en.json` has.

Components outside a provider speak English, so component tests query
English text without any setup.

## Adding a language

1. Add its code to `LOCALES` in `packages/domain/src/locale.ts`.
2. Add `packages/ui/src/i18n/<code>.json` with every key of `en.json`, and
   register it in `CATALOGS` in `i18n.tsx`.
3. Name it in itself in `LANGUAGE_NAMES` in `LanguageSelector.tsx`, and
   give it a flag in `FLAGS` (from flagcdn.com, as the others).
4. Give each plural message exactly the forms its plural rules name
   (`new Intl.PluralRules("<code>").resolvedOptions().pluralCategories`):
   only *other* in Korean, Japanese and Chinese; *one*, *many* and
   *other* in Spanish and French (*many* for a million and more);
   *one*, *few*, *many* and *other* in Polish and Ukrainian.
5. Register the file in the journeys' harness too: `Locale` and
   `CATALOGS` in
   [e2e/journeys/harness/strings.ts](../e2e/journeys/harness/strings.ts),
   and the language's name in `switchLanguage` in
   [e2e/journeys/pages/Chrome.ts](../e2e/journeys/pages/Chrome.ts).
6. Extend the tests that name every language: `locale.test.ts`,
   `i18n.test.tsx` (its catalogs, a plural, a date, a language's name),
   `LanguageSelector.test.tsx`, `PreferencesScreen.test.tsx`.
7. Name and define every topic in it in
   [ns/vocab/topics.ttl](../ns/vocab/topics.ttl), which holds its
   topics in the app's languages ([vocab.md](vocab.md)): the scheme's
   `dcterms:title` and `skos:definition`, and each concept's
   `skos:prefLabel` and `skos:definition`, with `owl:versionInfo` bumped
   and a `skos:changeNote` saying so. Then run `npm run format:turtle`,
   `npm run generate` and `npm run crosscheck`, and update the tests
   that compare topic labels (`concepts.test.ts`, `library.test.ts`).
8. If its script needs its own fonts, line breaking or heading
   treatment, add `:lang(<code>)` rules to `apps/web/src/style.css`, with
   tests in `style.test.ts`, as Korean has ([theme.md](theme.md#korean-text)).

The shapes' `sh:message`s stay in English and Swedish: a new language
needs none, and its readers see a shape's own message in English, marked
so, and the validator's messages in their language
([shapes.md](shapes.md#conventions)).
